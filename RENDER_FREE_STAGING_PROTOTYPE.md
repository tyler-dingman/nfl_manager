## Implementation and transaction boundary

Read [the prior CPU diagnosis](FIREBASE_CPU_ROOT_CAUSE.md) first. This prototype implements its proposed execution alternative without changing Firebase identities, SQL schemas, content IDs or shard routing. The Node API is compiled from the same existing 201-route registry. [The Node origin](src/server/node-staging/origin-server.ts) wraps the existing API and Next handler in request-scoped MultiD1 bindings; the Cloudflare default remains unchanged. The only shared application changes are an opt-in authenticated Node session transport and honoring an explicitly supplied runtime binding.

The [server-only REST adapter](src/server/node-staging/d1-rest.ts) pins the reviewed account/ten-owner IDs, validates immutable configuration, binds values/blobs, rejects foreign-owner statements, multi-statement SQL and oversized inputs/results, uses manual redirects/10 second timeouts, sanitizes errors and never automatically retries ambiguous outcomes. Its600 requests/5 minutes budget is shared across ten owners in one process. It is a conservative local guard, not an account-wide quota monitor; replicas, restarts, dashboard and other API consumers are outside that counter.

Cloudflare's [REST reference](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/) describes multi-query batch bodies but does not establish an explicit rollback guarantee equivalent to binding `batch()`. The [open transaction-semantics question](https://github.com/cloudflare/developer-platform/issues/79) is corroborating uncertainty, not proof that REST is non-atomic. Required operations include atomic ownership/session association, write-fence compare-and-set assertions, command idempotency, recovery integrity and origin nonce claims. Sequential substitution would be unsafe. Consequently the adapter rejects every real REST batch and mutation **before HTTP**, including apparently read-only batches. Only single SELECT/EXPLAIN statements are eligible remotely. There is **no environment bypass**; the atomic fixture option is restricted to loopback HTTP.

The fixture's ten disposable Miniflare databases execute each REST batch with one native binding batch. Tests prove the adapter preserves a trusted transport's behavior, including rollback after a later constraint failure; they do not validate Cloudflare's remote implementation. Coordinated backup/restore uses empty local targets and the current independent erasure ledger; original IDs and cross-shard references survive, while corrupt archives fail before mutation. No occupied or production database was touched.

## Origin authentication and session safety

The [edge entrypoint](workers/staging/render-origin.ts) is opt-in and unreferenced by existing deployment configs. It preserves the current staging credential gate and gated asset dispatch. A future deployment must pair `assets/` with the same Node build and set `run_worker_first=true`. The proxy accepts only a configured HTTPS Render root, signs requests, forwards no raw identity headers, disables redirects/retries and times out after15 seconds. No Render URL or credential was invented.

Assertions last20 seconds, have a random 192 bit nonce and bind canonical public origin, path/query, method, audience, signed application headers and SHA-256 body digest. Origin authentication precedes every API, SSR and direct static request. A unique claim in the existing D1_USERS assertion table serializes concurrent replay attempts across instances; maintenance locks deny claims. Restoring nonce history requires stopped traffic and at least30 seconds of expiry time before reopening. The independent erasure ledger is unchanged.

These assertions establish transport provenance, not user authorization. Existing Firebase signature/issuer/audience/expiration/UID verification, live provider revocation metadata, D1 tombstones/session lookup, ownership and account erasure remain active. No successful authorization decision is cached. Raw forwarded/client-IP values are dropped, conservatively sharing the Node unknown-client rate bucket; per-client rate-limit fidelity needs a separately reviewed Cloudflare-managed IP assertion before hosted use. Public clients cannot inject a trusted identity.

The starter pins the existing staging Firebase project/domain/app ID and staging public origin, requires D1/Firebase/disabled-legacy-password settings, disables telemetry, checks disabled automation/provider flags and rejects known external provider credentials. Origin/application/gate secrets must be independent and private. No production secret is copied into the prototype. Startup configuration and safe reproduction are in [the runbook](scripts/render-staging/README.md).

## Free-tier feasibility

Render documents Free Node web services with **0.1 CPU/512 MB**. These allocations do not establish that this application fits. [Compute plans](https://render.com/docs/compute-plans).

Free instances share750 monthly hours, sleep after15 idle minutes and may need about a minute to wake. Filesystem state is ephemeral; durable state here stays in D1. Excessive service-initiated external database/API traffic can cause suspension; D1 REST and live Firebase checks make that restriction directly relevant. Free services cannot receive private-network traffic, so the public HTTPS origin must enforce assertions. Render advises against production use. [Free service documentation](https://render.com/docs/free). Documented [no-payment setup](https://render.com/docs/your-first-deploy) does not verify this owner's eligibility or remaining allowance.

A roughly one-minute cold start exceeds both the15 second proxy timeout and20 second assertion. Expected behavior is failure closed on the first sleeping-origin request. A newly authenticated request with a fresh nonce may succeed after wake; automatic mutation retries are deliberately absent. Cold-start UX and existing idempotent-command recovery need hosted validation. A paid always-on instance is not authorized or recommended as an implicit workaround.

Cloudflare's API has a shared1,200 requests/5 minutes ceiling and200 requests/second per IP; application traffic plus administration/dashboard competes for it. REST amplification from nonce claims, SSR session checks and existing storage operations can constrain this prototype well before D1 storage limits. Cloudflare recommends an authenticated binding-backed proxy for application traffic and describes REST as better suited to administration. This is a feasibility warning, not an implemented architecture change. [API limits](https://developers.cloudflare.com/fundamentals/api/reference/limits/), [D1 application-access guidance](https://developers.cloudflare.com/d1/tutorials/build-an-api-to-access-d1/).

D1 Free retains ten databases, 500 MB per database and 5 GB per account, with 100 bound parameters and 100 KB SQL per statement. Daily included usage is 5 million rows read and 100,000 rows written; indexes and the durable replay ledger also consume writes. The adapter preserves numeric response metadata, but this local mission cannot report actual account headroom. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 usage allowances](https://developers.cloudflare.com/d1/platform/pricing/).

Firebase lists signup limits of100 accounts/IP/hour and Spark password-reset email 150/day. Identity Platform Spark daily-user limits apply only when that product is enabled; this mission did not re-verify project configuration or quota usage. No live account, reset email, AI, sportsbook, push or ingestion call occurred. [Authentication limits](https://firebase.google.com/docs/auth/limits).

The next owner decision is whether the unresolved REST transaction contract and Free availability/traffic limits justify a separately scoped hosted feasibility experiment. Until then retain remote write refusal and private staging. There is no deployment authorization exercised by this mission, no resource creation, billing activation, database migration, production/Vercel/downdistance.com change, or production readiness claim.
