# Zero-cost production readiness — Down & Distance

October 16, 2026. Base `074f0e60`; isolated branch `poc/zero-cost-production-readiness`, worktree `/private/tmp/down-distance-zero-cost`.

## Executive summary

**CONDITIONAL — specific remaining requirements.** A lean editorial D1 + R2 service plausibly fits $0 at 100 and 1,000 DAU. The complete existing product is **not production-qualified at $0**. In particular, the retained Neon Free polling scenario fails even without audience traffic (detailed below): live Worker CPU, actual account headroom, Next.js/Node hosting, PostgreSQL/pgvector, open-source model hosting, email delivery and complete application integration remain unverified. No production system, billing account, secrets file, paid service or deployment was accessed. No user/editorial source data was deleted. No push or merge occurred. Only disposable synthetic fixture rows/objects were retired or corrupted for recovery tests.

Select **A: lean D1 discovery metadata and immutable, self-describing R2 documents**, with a second verified private object copy. Keep user/transactional data and search on their existing paths until those services have a separately verified cost and migration decision. This is a working isolated implementation, including execution inside local workerd, not an enabled production replacement.

The earlier 350 MB target was an engineering target, not a Cloudflare limit. The applicable single-database cap is 500 MB; this evaluation uses **400 MB** as its 20%-margin budget. The selected 365-day D1 estimate is **321.16 MB**, with **6,025.14 MB of R2** including both payload copies, eight full D1 inventory backups and reserve, and **67,709 daily D1 writes** including queue and handoff costs. These are projections from local measurements, not production billing or a year-long load test.

**5,000 DAU does not fit this model:** 211,984 dynamic Worker requests/day and 16.98 million R2 Class B operations/month exceed the published included allowances. There is no silent paid fallback. The estimated capacity with assumed traffic/fan-out/cache behavior is **1,765 DAU**, falling to **1,092** if every public cache miss hydrates 20 objects. Qualified whole-product capacity remains **unverified (zero DAU certified)**. Start with a controlled 100-DAU launch only after the blockers below close.

## Root causes and ingestion changes

The prior 365-day projection was 474.18 MB standard / 535.87 MB entropy **after conditional synthetic cleanup**. It retained 1,142 immutable blob identities per daily cohort, separate fragments, compact JSON trees, record-level archive directories and operational ID indexes. The empty body identity/location rows alone took about 438 KB per cohort. Large source text remained pinned in D1 until byte retirement; R2 upload did not imply D1 reclamation. See the prior [storage report](workers/content-engine/D1_R2_STORAGE_FINAL_RESULTS.md) and [archival report](workers/content-engine/D1_R2_ARCHIVAL_POC_RESULTS.md).

Original local measurements show about 30.26 writes per new candidate, 22.05 per correction and 10.03 per source check, with additional compaction work. The existing queue itself costs **26 writes/job** for enqueue/claim/complete: measured 1,300 writes for 50 jobs, extrapolated to **36,400/day for 1,400 jobs**. Those lease, guard and idempotency writes were retained, not assumed away.

The new design stores one complete source/editorial snapshot in R2 from inception. D1 keeps heads, minimal version discovery metadata, team indexes and compact terminal receipts. No per-text fragments or second payload-manifest directory are generated. Unchanged canonical documents return before any R2 put or D1 mutation; metadata commits remain atomic, and corrections preserve original identities and revision chains. Publication decisions/cards/evidence pins are separately retained as immutable receipts, not discarded to improve the benchmark.

An early OR-based receipt lookup scanned growing groups: **3,209,146 D1 reads** in one cohort. It was replaced by two indexed `UNION ALL` probes. Team-identity updates have their own index, and feed pagination uses an indexed tuple seek. The final cohort reads **7,381 rows** with the indexed implementation. Exact plans and the superseded summary are retained. No scheduled frequency or AI-generation policy was reduced. Conditional requests/checkpoints, stable content hashes and unchanged-document skips support incremental work; no external feeds or model endpoints were called during validation.

News freshness remains the repository's eight global runs/day, and delivery checks remain every five minutes. Generate once per team/editorial date and only regenerate on a genuine input change using the existing fingerprint contract. Duplicate trial schedules remain disabled/manual; the authoritative global scheduler is unchanged. Parlay sportsbook refresh is modeled as **three times/week**, not daily, with an explicit 100-request/run planning allowance. Its real provider quota and payload volume remain unverified.

A supplemental measured 83 publication/card receipts is added to **every** option. Standard and poorly compressible source cases have identical lean metadata sizes because payload compression no longer determines D1 size.

A preserves indexed version/source discovery and constant-key revision lookup; no periodic content-payload cleanup is required. B writes the verified R2 copy at inception too, keeping recent inline snapshots for hot availability, then nulling only verified redundant hot values after 7/14/30 days. Its indexed retirement is bounded to eight rows/call. B's conservative footprint includes observed post-retirement page packing/fragmentation; it is not an assertion that unused space can never be reused. No VACUUM was used to manufacture savings. C keeps version history in self-describing linked R2 snapshots with only current D1 discovery. C is rejected despite smaller storage: indexed historical discovery is unavailable, and a 51-revision test demonstrates the explicit 50-hop traversal limit. Existing historical search must not be weakened.

All raw measurements include every SQLite table and index plus row/column inventories, file bytes, owned pages and freelist. Growth projections add 20% page reserve, 20 MB active-queue/control allowance and 10 MB migration scratch. They assume the safe terminal handoff is enabled after review; simply leaving all old completed jobs indefinitely in the active queue would invalidate this budget. No original production rows were retired. R2 is conservatively uncompressed, retains all snapshots and receipts indefinitely, includes **two complete logical copies plus 20% reserve**, and counts reads/writes for both-copy verification. The total also reserves seven daily coherent D1 exports and one monthly checkpoint at current peak size, with another 20% backup reserve. Export is conservatively charged as one D1 read per retained row plus 20,000 active/control rows; 512 KB backup chunks, verification reads and checkpoint writes are included. These are planning costs: the production coherent export/restore orchestrator is not implemented or deployed. The second copy is not provider-independent disaster isolation.

## Retained infrastructure: independent whole-product failure gates

The earlier integration audit `c785bbc5`, FO-1 finalization `afe79c90`, next-due scheduler `0dd422d5`, and Parlay plan `50190c9d` were inspected through local Git objects. Their measurements were not rerun or assumed deployed. The latest user instruction **overrides** the old five-weekday Parlay plan: this model uses three refreshes/week.

Current [Neon Free pricing](https://neon.com/pricing) includes 100 CU-hours/month, 1 GB/project and 5 GB transfer; use 80 CU-hours, 800 MB and 4 GB budgets. Default 0.25-CU compute suspends after five idle minutes. The current nominal five-minute delivery path reaches PostgreSQL even when no delivery is due. If kept awake through the month, `0.25 × 24 × 30 = 180 CU-hours`: **the unchanged polling scenario exceeds the free compute allowance even at zero DAU**. This is a documented-limit/scenario failure, not a fresh account-usage measurement. No missed polls or reduced delivery freshness are assumed as savings. A next-due gate must preserve arbitrary timezones and preference changes; concentrated-time savings from the prior POC cannot be applied to uniformly scattered users without testing.

Prior local FO-1 evidence reports ~2.31 MB PG result transfer for one roster read and similarly wide command reloads; the prior odds audit reports a 17.51 MB full-event PG response. A sensitivity in which only 20% of DAU performs one such read/day gives **1.386 / 13.86 / 69.30 GB/month** for FO at 100/1,000/5,000 DAU, and **10.51 / 105.07 / 525.33 GB/month** for full-event Parlay. Those are scenario calculations against named prior measurements, not new production observations or a claim all routes are that wide. They show why treating retained PG as free based only on SQL row counts is unsafe. Narrow, ownership-correct projections and eligible public odds caching must be reviewed before whole-product cost qualification. No Front Office or Parlay implementation was changed.

The current isolated branch does not contain the separate finalized FO-1 durable-route implementation. Passing baseline FO unit tests is not proof that the FO-1 migration, cross-process gameplay recovery, or FO-2 optimizations are integrated. That branch reconciliation is an explicit production blocker, rather than an implicit merge here.

Existing Node/native Argon2 dependencies and model services still require an eligible, verified host. The current whole-product architecture therefore **cannot be approved for $0 launch as-is**. The selected editorial implementation fixes a major cost source; it does not erase these independent constraints.

Production handoff needs a recovery window, monitoring, backpressure, bounded cursors and backup checks before any old terminal row is retired.
8. After a successful rollback and disaster-recovery rehearsal, consider a separately reviewed production cutover. Keep source and both R2 copies through the rollback window. No destructive migration or automatic source retirement is included.

## Rollback and disaster recovery

Before cutover, rollback is simply to keep reading the unchanged source. `importEditorialHistory` is additive/idempotent; `exportEditorialHistory` returns original kind/ID/revision payloads for replay. After a future cutover, stop new lean writes, preserve pending work and snapshot both systems, then switch reads to the intact original repository **only after replaying/verifying any post-cutover revisions**. Switching readers without that reconciliation can lose corrections. Export terminal receipts as well as articles, and reconcile generation/delivery dedupe before resuming schedulers. Never disable object readers while live pointers remain, and never delete either R2 copy during rollback.

For a damaged primary object, the mirrored reader returns only the independently hash-verified second copy and records degraded availability; it does not overwrite the corrupt primary. If both copies fail, reads fail closed and an operator must restore verified backup bytes. If D1 is unavailable, no fabricated feed or unvalidated inventory is returned. Total D1 loss requires a consistent relational/head/version/receipt inventory backup plus objects; self-describing snapshots do not identify which orphan writes were committed. Full source/database disaster recovery and provider-independent backup are still blockers, not features proven by the primary-object fallback test.

## Remaining blockers and next action

1. **Production CPU/subqueries and peak load:** local workerd compatibility is proven; Cloudflare Free-plan CPU is not. Whole-object hashing, full-feed hydration, native auth/SSR and model work cannot be assumed to fit 10 ms. Some multi-team/admin operations approach the 50-query boundary and need per-stage review.
2. **Complete API/ingestion integration:** the selected repository and authenticated loopback rehearsal work; production adapters, full query/ranking parity, durable stage orchestration and production-safe handoff are not enabled. Cold metadata equality alone is insufficient.
3. **Retained-infrastructure failure gates and non-editorial costs:** the nominal Neon polling scenario already fails the published Free compute budget; prior FO/Parlay transfer sensitivities also expose free-tier failures. Separate FO-1 integration is absent from this branch. In addition, PostgreSQL/pgvector and index growth, Next/Node runtime, model hosting, odds/API quotas, CI, email and provider/account plans were not inspected. Open source does not mean hosting/electricity is free. No account is declared free without evidence.
4. **Recovery and spend protection:** coherent graph backups, provider-independent recovery, restore drills, orphan inventory, immutable-copy monitoring, account R2 overage controls and rollback delta replay need staging validation.
5. **Real workload:** source size distribution, accumulated historical inventory, geography/cache eligibility, 11-versus-20 object fan-out, search popularity and registered-user delivery scans must be validated. The explicit worst-size workload does not fit R2's included storage.
6. **End-to-end product validation:** browser/native devices, real auth, email/push/TTS, grounded semantic search, saved-game/user data and sportsbook freshness were not exercised against a staged application.

**Next recommended action:** review this branch and approve a separately scoped Free-plan synthetic staging rehearsal plus the retained-service cost inventory; do not cut over production or enable paid plans. The honest outcome is a substantially leaner working local candidate and a bounded launch model, not a claim that the entire product is already production-ready at $0.
