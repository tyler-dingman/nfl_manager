My Parlay sportsbook compatibility fix
2026-10-10

1. Root cause
The proposal builder permitted an unpriced exact-match fallback when the destination sportsbook did not have a stored offer. Transfer eligibility then bypassed price/availability checks for those unknown-priced selections. The shared hook also automatically prewarmed FanDuel after adding a leg. Locally, FanDuel was the only enabled integration. Together these behaviors offered/generated FanDuel for a DraftKings-priced selection without a FanDuel offer.

This was not loss of the original bookmaker in parlay state: ResearchWorkspace uses the market's sportsbook and exact-threshold currentPrices; ParlayLabHome passes the full selection to addSlipLeg, which preserves its metadata. Research currentPrices and transfer queries both use normalized sportsbook_prices. Transfer matching now requires a destination-book price for every leg, independently of the original bookmaker.

3. Combined-yard transfer support
One read-only Unabated /bettype discovery request returned active player bet type 64, Passing and Rushing Yards, hasPoints=true, sides=ou. Evidence: reports/unabated-combined-market-discovery.json.
This establishes the provider's taxonomy, not DraftKings-specific text-generation coverage. Official documentation does not establish that this market can generate a DraftKings slip for this account. No live generation was performed or inferred successful.
Combined passing/rushing yards is therefore excluded from transfer capability pending book-specific verification. Its taxonomy, stored odds and Lab Score remain intact.
Local DraftKings, Caesars and BetMGM transfer flags are disabled; FanDuel is enabled for the local allowlisted test account. Flags were not changed. Shough's selection therefore correctly has NO eligible transfer button currently. Making him transferable requires verified provider/book coverage and a separately authorized integration rollout, not relabeling the FanDuel button.

4. Shared resolver and server safeguards
resolveSportsbookCompatibility in packages/parlay/sportsbook-transfer.ts evaluates each sportsbook independently. Its result distinguishes enabled, supported, eligible, exact/adjusted/unavailable, matched leg counts and storedExactLegs. Eligible proposals contain the sportsbook-specific selections and estimated combined odds.
Matching requires canonical event/player/market/side/period, available sportsbook-specific price, valid odds/threshold, unlocked event and future kickoff. Provider mapping must belong to the canonical player. Missing selected IDs or unsupported markets prevent a complete proposal. Existing duplicate-selection and same-game restrictions remain.
No stored deep link is required when a supported, priced selection can be generated through Unabated.
The preview API invokes only the PostgreSQL proposal service. Start verifies enabled flags, refreshes and validates the signed complete proposal, requires explicit adjustment approval, and rechecks stored availability before generation/quota reservation. An enabled feature flag alone never creates a proposal.

5. Button and multi-leg behavior
Web and native consume the same shared resolver-backed hook. Buttons are shown alphabetically only for enabled integrations with complete eligible proposals. Adding/removing a leg invalidates stale buttons and URLs immediately, then checks the new complete slip. DraftKings-only plus both-book legs yields DraftKings only; disjoint coverage yields neither unless an eligible complete adjusted proposal exists. Removing a restrictive leg reveals newly eligible books without manual refresh.
Each button uses its own book's prices, including adjusted-line prices, marked Est. Existing branded buttons/logos, action disclosure, save/share/export and error handling remain.
The old legacy stored-deep-link fallback was removed from both renderers so it cannot bypass flags or complete-slip checks.

6. Substitutions
The existing closest eligible alternate-line matching and bounded substitution policy are retained. Event, player, market, direction and period never change. The button indicates adjustments; confirmation shows original/proposed thresholds. Generation occurs only after explicit approval. Cancel leaves the user's original parlay unchanged. Signed proposals are checked again server-side; approval never silently changes My Parlay selections.

7. Refresh and request behavior
Recheck Stored Availability is a styled secondary button with a loading state. It fetches local integration capabilities and re-queries PostgreSQL; it does not refresh odds from SportsGameOdds or generate through Unabated. Empty compatibility explains that stored odds cannot support a complete eligible slip. Save/share remain available.
Automatic FanDuel prewarming was removed. Adding/removing legs, waiting, and rechecking do not generate links. Only explicit selection/adjustment approval generates. Existing deduplication, durable quotas, pending-job handling, validated URL navigation, expiration, cancellation, partner attribution and production restrictions are preserved.

10. Remaining limitations and safety
Stored weekly odds may no longer match the sportsbook. Database compatibility prevents unsupported attempts based on known data but is not a guarantee of live generation success.
DraftKings combined-yard transfer coverage remains unverified despite discovery bet type 64. Same-game transfers remain excluded by existing integration restrictions; hypothetical same-game examples do not override that restriction.
The provider can omit Over/Under direction in generated results; existing response validation and user review requirements were not weakened or represented as independent direction verification.
No production transfers enabled. No feature flags, quotas, partner attribution, SportsGameOdds ingestion, stored prop data or Lab Score changed. No live Unabated generation requests were made during this task or automated tests.
