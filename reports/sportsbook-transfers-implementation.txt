MULTI-SPORTSBOOK TRANSFERS — IMPLEMENTATION

STATUS
Implemented web, mobile web and React Native adapters for DraftKings and FanDuel using the existing generation client and durable jobs. DraftKings defaults off; FanDuel retains its existing test flag. Both remain inaccessible in production through the existing NODE_ENV gate. Local feature flags and the authenticated test-user allowlist were not edited.

No SportsGameOdds requests, ingestion changes, Lab Score changes or odds-table writes. The local transfer-jobs table received only an additive sportsbook column. Existing jobs, actor hashes and quota history remain intact. No production operation was performed.

COMPATIBILITY AND SUBSTITUTION
A debounced, authenticated preview request reads PostgreSQL after slip changes. It never calls Unabated. Both configured books are evaluated independently and presented alphabetically. Unsupported books have no button. If neither is compatible, save/share/export remain available.

The server resolves original market UUIDs to canonical player/game/market/side/period/threshold values. Candidate queries require the same event, player ID, market, side and period; only the numeric line can differ. The initial supported markets remain passing yards, rushing yards, receiving yards and receptions. Other markets remain unavailable pending supported matching/validation. All events must be future, unlocked SportsGameOdds events. One prop per game and 1–20 unique selections remain required.

Exact thresholds take priority. Otherwise candidates rank by absolute threshold distance, then easier direction (lower Over/higher Under on equal distance), optional existing score, latest price timestamp, then stable ID. The service does not calculate or fabricate scores; the current database query has no persisted Lab Score to attach, so that optional tie-breaker is unused for current DB rows.

Default maximum changes: passing yards 10; rushing yards 7.5; receiving yards 7.5; receptions 1. Configurable through TRANSFER_MAX_DIFF_<MARKET>. Invalid/unbounded differences become zero. Substitutions must have a known main/alternate classification from the existing classifyStoredLine helper and stored odds at least -800 by default. TRANSFER_MIN_SUBSTITUTE_ODDS uses the existing supported alternate-odds options. Exact existing selections are not silently replaced because of price preferences. No thresholds or prices are invented.

CONSENT AND ESTIMATES
An adjusted button states the adjustment count. Clicking it shows each original/proposed line, substitute price and estimated book-specific combined odds, with Continue with Adjustment and Cancel. No generation request occurs until approval. Original My Parlay selections are never changed.

Server-signed, five-minute proposal tokens bind the user, sportsbook, original IDs, exact proposed values/prices and expiry. Start re-reads the database, recomputes the proposal, verifies its signature and checks every value. Changed lines, prices, availability or expired tokens require a fresh review. A client cannot submit arbitrary names, prices or substitute IDs. The server rejects unapproved adjustments.

Each book's estimated combined odds use its own matched prices through the existing slipOdds helper. Prices are clearly estimates; weekly data does not guarantee current sportsbook availability. Final sportsbook prices take precedence.

GENERATION AND VALIDATION
POST /api/parlay-lab/sportsbook-transfer supports preview, start and poll. GET reports only the authenticated account's enabled books. The prior FanDuel endpoint remains compatible for old clients and uses the same jobs and counters.

One explicit choice generates the entire approved slip in one documented Unabated text request. Book-specific prompt, eligibility and validation use the requested book, not the source of the original prop. Returned book, count, each player/game/kickoff/market/full-game period/exact numeric threshold, explicit direction/region contradictions and duplicate/missing legs are checked. DraftKings mismatched thresholds are rejected even if all legsMatched counts claim success.

Each book has an explicit URL adapter. Both currently allow only the HTTPS Gambly cache URL format actually observed for that book in prior diagnostic responses. This is not an assumption about identical FanDuel/DraftKings private URL formats; no private sportsbook URLs are constructed. Partner attribution is preserved/validated using URL parsing. Missing direction remains directionVerified:false; production is still blocked.

Generation stays inline. Loading and cancellation do not open tabs or native apps. On validation success each book shows its own ready state and Continue link. Continue alone opens the returned Gambly destination. The proposal area scrolls within the existing panel/sheet so multiple adjustments do not obscure the original slip or save/share controls.

SHARED SAFEGUARDS
The existing fanduel_transfer_jobs table name and HMAC actor namespace are retained to preserve history. Migration 052 adds sportsbook, defaulting old rows to fanduel. Fingerprints include the sportsbook and approved selection IDs. Both books share one advisory lock and the same daily/concurrency counters: 5/user/day, 50 globally/day, 3 concurrent (configurable downward). One recent active reservation/user, bounded polling, no automatic POST retries, failed attempts count, and deduplication remain. The new endpoint checks each book's flag for both start and poll. ENABLE_DRAFTKINGS_BETSLIP=false is documented in .env.example. Both use FANDUEL_TEST_USER_IDS, intentionally reusing the existing allowlist rather than introducing a separate authorization path.
