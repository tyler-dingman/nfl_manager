## Free-plan evidence and runtime choice

The [Firebase pricing plan documentation](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans) describes Spark without payment information and supports production apps. It does not impose a noncommercial-only restriction on the documented no-cost authentication path. This implementation uses email/password, not a billing-dependent phone/SMS or external password execution service. The actual signed-in console independently displayed Spark / No-cost ($0/month) for the existing project on October 20, 2026; this is not a fresh Cloudflare account/quota audit.

The [authentication limits](https://firebase.google.com/docs/auth/limits) list Spark password-reset mail at 150/day, address-verification mail at 1,000/day, email-link sign-in at five/day and account creation at 100/hour/IP. For Authentication **with Identity Platform**, instrumentless Spark limits include 3,000 Tier-1 DAU and two Tier-2 DAU. Those conditional Identity Platform figures are not an assertion that this uninitialized project has been upgraded or its actual quota consumption measured. Target 25–50 DAU does not replace account/abuse/quota verification; quotas may change and limits fail requests rather than authorizing billing.

[Firebase ID-token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens) documents public-key verification for another runtime. Here `jose` and WebCrypto verify RS256 against Google's fixed Secure Token JWKS endpoint, with exact issuer/project audience, mandatory expiration/issued/authentication times and bounded nonempty UID. No emulator token, caller key URL or unverified client UID can select a D1 user. [Firebase REST](https://firebase.google.com/docs/reference/rest/auth) supplies account lookup/deletion with the user's ID token and public API key, without a privileged Admin key. Every protected app session validates current provider state and `validSince`; missing metadata/outage fails closed. Real-project availability of this metadata is an explicit hosted gate, not inferred from fixture success. [Session documentation](https://firebase.google.com/docs/auth/admin/manage-sessions) identifies password reset/account changes as revocation events; local tests simulate these transitions, while actual provider behavior still requires live qualification.

The [Expo Firebase guide](https://docs.expo.dev/guides/using-firebase/) supports the Firebase JS SDK and requires version 12+; Expo SDK 54 instructions were inspected through the [versioned SecureStore source](https://raw.githubusercontent.com/expo/expo/sdk-54/docs/pages/versions/v54.0.0/sdk/securestore.mdx) because the published archived documentation URL redirects to latest. Native SDK state uses SecureStore with bounded chunking and a generation manifest; browser SDK state uses session persistence. These contain user-scoped SDK credentials, never Admin/service-account credentials. The product cookie remains opaque, HttpOnly, Secure in production, SameSite=Lax. The Worker retains only an encrypted, short-lived provider ID token associated with the opaque app session; it does not persist Firebase refresh tokens or passwords in D1.

## Implementation and data safety

`POST /api/auth/firebase/session` performs the signed-token/online account checks, stable UID mapping and app session issuance. Web keeps the existing cookie/SSR service-binding contract; native keeps its existing app bearer-token API transport. App session expiration is capped to the Firebase ID token, rather than allowing a long-lived local cookie to outlive verified identity. SDK token refresh re-exchanges a fresh verified token; only the caller's previous same-user app session may be revoked. Normal Firebase operations never call the internal password Worker. Web observer cleanup prevents old login-screen callbacks from redirecting users during later token refresh; logout waits for exchanges before clearing app state. Native logout waits for a pending refresh and revokes the latest saved app token.

Migration `0010_firebase_auth.sql` adds provider-session associations, hash-only revocations and a durable deletion journal to **D1_USERS only**. No app-state store is moved and no database is recreated. Existing test accounts are neither deleted nor automatically linked on matching email. New verified Firebase identities create an application UUID without an app_credentials password row. Existing preferences, Front Office, saves, trivia and other data continue to use that UUID. A conflicting legacy test email is rejected; the owner can use a new synthetic alias or explicitly review an export and mapping/erasure procedure first.

Missing configuration selects Firebase fail-closed mode; it never falls back to local password hashing. Legacy operation requires both `AUTH_PROVIDER=legacy` and `APP_LEGACY_AUTH_ENABLED=true` and is used only in explicit offline regression/rollback fixtures. Both staging API/Web configs select Firebase, disable password execution and keep `FIREBASE_AUTH_ENABLED=false` until the owner supplies/reviews real values. Worker public subdomains/previews remain false, internal workers remain private, assets still run through the existing staging gate, and provider/ingestion/mail/background flags remain disabled. No hosted settings were changed or newly verified in this mission.

A Firebase deletion must prove a current authorized application session and recent same-user identity. Provider deletion is acknowledged before the existing D1 erasure request; partial failures preserve evidence for a bounded owner-only resumption. Existing independent erasure-ledger behavior is preserved. The additional encrypted Firebase ledger must be current and retained independently of old backups; monotonic replay preserves newer revocations/deleted UID tombstones. See the [interruption/recovery procedure](reports/firebase-auth/hosted-retest-plan.md#erasure-interruption-and-recovery). Hosted restore remains **UNVERIFIED**; no occupied databases were touched to manufacture capacity.

Email changes through independent legacy D1 email-token routes now return 409 in Firebase mode, preventing identity/email divergence. Completing provider-managed address verification is a separate outstanding product gate. Firebase password reset uses the default Firebase-hosted action handler; actual sender delivery, action completion/replay and return-to-app behavior are unverified until setup. Existing application transactional mail/push remains disabled.
